# План розробки

Стек: TypeScript (strict), pnpm workspaces, Node 24.
- `packages/engine` — чистий детермінований рушій правил без залежностей: seed RNG, стан, дії, replay, підрахунок.
- `packages/protocol` — zod-схеми повідомлень клієнт ↔ сервер.
- `packages/bots` — боти, що працюють поверх рушія.
- `apps/server` — Fastify + Socket.IO, авторитетний сервер. Кімнати, event-sourcing: у сховищі лежать seed і лог дій (SQLite; адаптер можна замінити).
- `apps/web` — React + Vite, mobile-first PWA.
- Тести: Vitest, fast-check, Playwright, Stryker.

Формат: `ID — назва` · залежності · критерії приймання. Етап **M0** виконуємо в цій сесії разом:
автопілот ще не існує. Починаючи з **M1**, задачі йдуть в issues, і їх беруть агенти.

## M5 — Запуск

Рішення власника (01.10): **Render** (безкоштовний web service для сервера + статичний сайт для клієнта) і **Neon**
(безкоштовний Postgres, регіон Франкфурт) для збереження кімнат. Вимога: гра продовжується після засинання сервера
(15 хв без трафіку) і після кожного передеплою.

- **T50 — Вибір хостингу** · T33 · Вирішено: Render + Neon (див. вище). Акаунти й секрети створює людина.
- **T54 — Сховище кімнат у Postgres** · T33 · Асинхронний `RoomStore` і `PostgresRoomStore` (`pg`), схема створюється/мігрується під час старту. Дія підтверджується клієнту лише після запису в базу; записи однієї кімнати йдуть послідовно. Кімната (разом із токенами гравців) підвантажується з бази за кодом при перепідключенні, а не лише під час старту. Після відновлення продовжуються ходи ботів і пауза після взятки. Повторні спроби при «холодному» старті Neon. Очищення: завершені ігри старші 30 днів, лобі старші 7 днів. Тести на справжньому Postgres (service container у CI); `MemoryRoomStore` лишається для unit-тестів.
- **T55 — Безперервність гри: засинання й передеплой** · T54 · На SIGTERM сервер перестає приймати дії, дописує все в базу, надсилає клієнтам `server:restarting` і закривається. Клієнт перепідключається без ліміту спроб (backoff до 5 с), показує «Сервер прокидається, зачекайте до хвилини…» і сам повертається в кімнату на той самий хід. При зміні `protocolVersion` сторінка перезавантажується, токен зберігається. Під час відкриття сторінка одразу пінгує `/health`, щоб будити сервер. E2E: гра з ботами → SIGTERM посеред взятки → новий процес через 60 с → гра продовжується з того самого стану (mobile-360 і desktop).
- **T56 — Сумісність збережених ігор між версіями** · T54 · Фікстури логів незавершених ігор у `packages/engine/test/golden/compat/` (`spec-change`); CI перевіряє, що поточний рушій їх відтворює. Для несумісних змін — `ENGINE_LOG_VERSION` і міграція або зрозуміле повідомлення гравцям.
- **T51 — Деплой-пайплайн (Render + Neon)** · T55 · `render.yaml` (Blueprint): web service сервера (регіон frankfurt, `healthCheckPath: /health`, `DATABASE_URL` і `PUBLIC_URL` з оточення) і static site клієнта (`VITE_SERVER_URL`); автодеплой з main. `deploy.yml` чекає завершення деплою через Render API, проганяє smoke e2e на проді, при падінні відкочує через Render API і створює issue `bug P0`.
- **T52 — Кнопка «Повідомити про баг»** · T51 · issue з replay-файлом, AUTOPILOT §6.
- **T53 — Nightly-прогони** · T51 · Зроблено власником: `.github/workflows/nightly.yml` — 100k симуляцій, mutation (скрипт `mutation`, якщо є), smoke на проді; падіння → issue `bug` + `agent:ready`.
- **T57 — Mutation testing рушія (Stryker)** · T53 · `packages/engine`: Stryker для Vitest, скрипт `pnpm mutation` (звіт у `packages/engine/reports/mutation/`), поріг `break` ≥ 80% mutation score; не в `pnpm verify` (лише nightly). Якщо score нижче — дописати тести, а не знижувати поріг.

## M6 — Покращення після першої гри (ідеї власника, 01.10)

- **T60 — Опції кімнати: «Темна» і «не більше трьох нулів поспіль»** · T17 · R-10.1–R-10.3 (`spec-change`: нові golden-сценарії). Рушій: опції в `createGame`/логу й replay; темна роздача в розкладі перед мізером; бали ×2; `viewFor` не віддає руку до кінця замовлень у темній (сервер не надсилає карти — перевірити тестом протоколу); заборона четвертого 0 поспіль. Боти вміють замовляти наосліп. Сервер і протокол: налаштування опцій хостом у кімнаті очікування, видно всім. Клієнт: перемикачі в кімнаті очікування (за замовчуванням вимкнені), «Темна» в розписці позначена окремо, під час темних замовлень рука показана сорочками. Golden-сценарії на кожне правило, property-тести з увімкненими опціями, `R-10.*` прибрати з pending.
- **T61 — Розписка: «замовив → взяв» і влучання** · T45 · У клітинці замовлення показувати `3→3` (замовив → взяв) з кружечками за джокерів; колір/позначка «влучив» (взяв рівно) чи «не влучив», не лише колір (доступність). На mobile-360 вміщується без горизонтального скролу (правила з `CLAUDE.md`).
- **T62 — Звуки і привітання переможця** · T47 · Тихі звуки (Web Audio, без зовнішніх файлів або з маленькими вбудованими): свій хід, зіграна карта, взятка, кінець роздачі. Кнопка «звук увімк/вимк» поруч із вібрацією, вибір зберігається; звук стартує лише після дії користувача. Фінальний екран: «🏆 Вітаємо, <ім'я>! Перемога з N очками» (нічия — кілька імен, R-9.4), анімація з урахуванням `prefers-reduced-motion`.
- **T63 — Голосовий чат у кімнаті** · T55 · WebRTC (mesh до 6 гравців), сигналінг через наш Socket.IO, публічні STUN; кнопка мікрофона (вимкнено за замовчуванням), індикатор, хто говорить, вимкнення звуку інших. Працює лише через HTTPS (Render) — на HTTP кнопка пояснює це. Перепідключення після засинання/деплою відновлює голос. Тести: unit сигналінгу на сервері, e2e з фейковим медіапристроєм Chromium (`--use-fake-device-for-media-stream`) для 2 гравців.
