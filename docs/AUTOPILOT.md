# Автопілот: система розробки, контролю і тестування

Мета: код пишуть, перевіряють, мерджать і деплоять агенти (Claude Code). Людина лише
відповідає за правила гри, грає й повідомляє про баги, а також розбирає рідкісні
тікети `needs-human`.

## 1. Загальна схема

```
 docs/PLAN.md ──(scripts/sync-plan)──► GitHub Issues (бэклог)
                                              │  label: agent:ready, deps закриті
                                              ▼
 cron / merge ──► [dispatch] ──► [implement: Claude Code] ──► PR "Closes #N"
                                                               │
                        ┌──────────────────────────────────────┤
                        ▼                                      ▼
                     [CI gates]                         [review: Claude, окрема роль]
                        │ fail                                  │ changes requested
                        ▼                                       ▼
                     [fix: Claude] ◄───────────────────────────┘   (≤3 спроби → needs-human)
                        │ green + review ✓
                        ▼
                  auto-merge (squash) ──► main ──► [deploy] ──► smoke e2e на проді
                                                                │ fail
                                                                ▼
                                                       auto-rollback + issue bug
 Гра ──(кнопка «Баг»)──► issue з replay-логом ──► agent:ready (пріоритет P0)
 Нічні прогони (100k симуляцій, mutation, e2e на проді) ──► issue при падінні
```

## 2. Джерела істини і захищені файли

| Файл | Хто змінює |
|------|-----------|
| `docs/RULES.md` | людина або агент через PR з міткою `spec-change`, яку ставить людина |
| `packages/engine/test/golden/**` — еталонні сценарії, похідні від RULES.md | так само, як RULES.md |
| `.github/workflows/**`, `apps/web/smoke/**` (smoke на проді), `CLAUDE.md` (розділ «Правила агента») | так само |
| усе інше | агенти вільно |

Workflow `guard` відхиляє PR агента, який торкається захищених шляхів без мітки
`spec-change`, поставленої власником репозиторію. Мітку перевіряють через GitHub API:
хто її поставив. Так агент не може «полагодити» тест, послабивши його, або переписати правила.

## 3. Мітки issues

- `agent:ready` — задачу можна брати, якщо всі `Depends on #…` закриті.
- `agent:in-progress` — задачу взяв агент (одночасно лише одна).
- `agent:attempt-1..3` — лічильник спроб фіксу.
- `needs-human` — агент застряг або задача потребує рішення людини.
- `bug`, `P0` / `P1` / `P2`, `epic:*`.
- `spec-change` — дозвіл змінювати захищені файли (ставить лише власник).

## 4. Workflows (GitHub Actions)

| Workflow | Тригер | Що робить |
|----------|--------|-----------|
| `ci.yml` | PR, push у main | `pnpm verify`: lint, typecheck, unit + property, golden, симуляція 10k ігор, build, Playwright e2e (мобільний + десктоп), пороги coverage |
| `guard.yml` | PR | перевіряє, що захищені шляхи змінені лише з дозволу |
| `agent-dispatch.yml` | cron кожні 30 хв (резерв; GitHub часто затримує розклад), push у main, ручний запуск | якщо немає відкритого PR агента, що ще в роботі, бере **пакет** до `AGENT_BATCH_SIZE` задач `agent:ready` одного етапу (P0 → P2, потім за номером). Залежності кожної задачі мають бути закриті або входити в той самий пакет. Задачі зі `spec-change` завжди йдуть окремо. PR, які чекають лише на людину (`spec-change` або `needs-human`), чергу не блокують; одночасно відкрито не більше 2 PR агента. Ставить `in-progress` і запускає implement |
| implement (job у dispatch) | з dispatch | Claude Code CLI виконує задачі пакета по черзі за TDD, по коміту на задачу. Відкривається один PR з `Closes #…` для кожної виконаної задачі. Якщо агент зупинився посеред пакета, виконані задачі йдуть у PR, задача, на якій він зупинився, — людині, решта повертається в чергу |
| `agent-review.yml` | PR агента, зелений CI | окремий запуск Claude з роллю рецензента: звіряє зміни з RULES.md і критеріями приймання, шукає послаблені тести та невідтестовані гілки. Результат публікує як status check `agent-review` |
| `agent-fix.yml` | CI червоний, `agent-review` = changes, або PR конфліктує з main (dispatch перевіряє відкриті PR і ставить `agent:conflict`) | Claude виправляє. Після 3 невдалих спроб ставить `needs-human` і надсилає сповіщення |
| auto-merge | branch protection | обов'язкові checks: `verify` (CI), `guard`, `agent-review`. Після них — squash-merge |
| `deploy.yml` | push у main | Render сам деплоїть кожен коміт main (`render.yaml`); workflow через Render API чекає деплою цього коміту, проганяє smoke (`apps/web/smoke/`) на проді. Збій збірки → issue `bug P0`; збій smoke → відкат сервісів до попереднього деплою + issue `bug P0` |
| `nightly.yml` | cron щоночі | 100k симуляцій, mutation testing рушія (Stryker, поріг ≥80%), e2e на проді, оновлення залежностей. Будь-яке падіння — issue `agent:ready` |
| `digest.yml` | cron щодня | коментар у закріпленому issue «Щоденний звіт»: що змерджено й задеплоєно, що заблоковано, витрати на запуски агентів |

## 5. Рівні тестування

1. **Unit**: кожне правило `R-x.y` має щонайменше один тест, у назві якого є його ідентифікатор. Скрипт `scripts/rules-coverage` падає, якщо якесь `R-…` з RULES.md не покрите.
2. **Golden-сценарії**: вручну описані роздачі з відомим результатом (руки, ходи, взятки, бали). Захищені файли.
3. **Property-based** (fast-check): для будь-якого seed і будь-якої послідовності легальних ходів:
   - кожна карта зіграна рівно один раз;
   - сума взяток дорівнює кількості карт у роздачі;
   - сума замовлень ≠ кількості карт;
   - перерахунок балів з логу дає ту саму таблицю;
   - replay(log) дає той самий стан.
4. **Симуляція**: 10k (PR) і 100k (nightly) повних ігор для N = 3…6, де грають випадкові та евристичні боти. Seed, що впав, автоматично стає регресійним тестом.
5. **Інтеграційні**: сервер + кілька віртуальних клієнтів через WebSocket: кімната, гра, перепідключення, рестарт сервера посеред гри.
6. **E2E** (Playwright): 4 браузерні контексти (iPhone, Pixel, Desktop Chrome/Firefox) проходять гру з ботами. До цього входять скриншот-перевірки ключових екранів і перевірки доступності (axe).
7. **Smoke на проді** після кожного деплою.

## 6. Відтворюваність і баги

- Кожна гра — це `seed` плюс лог дій. Стан завжди можна повністю відновити через `replay`.
- Кнопка «Повідомити про баг» у грі створює issue з описом, скриншотом і replay-файлом. Серверний GitHub-токен має лише право писати issues.
  - Реалізація T52: issue з описом і replay-файлом, мітки `bug`, `P0`, `agent:ready`. **Скриншот не додається:** REST API GitHub не приймає вкладень в issues — це рішення винесене на погодження власника.
  - Replay містить `seed`, з якого видно всі карти, тому звіт, надісланий посеред гри, зберігається в знімку кімнати (переживає рестарт і деплой) і публікується після завершення гри або коли гру покинуто (без змін понад 24 год).
  - Захист від спаму: не більше 3 звітів від гравця з однієї гри, 10 на годину на весь сервер і 3 на годину з однієї IP-адреси (далі — `rateLimited`).
  - Токен — `BUG_REPORT_TOKEN` на Render; без нього кнопка повідомляє, що звіти недоступні.
- Агент, який бере баг, спершу відтворює його через `pnpm replay <file>`, потім пише тест, що падає, і тільки тоді виправляє.

## 7. Керування, обмеження витрат і безпека

**Змінні репозиторію** (Settings → Variables, або `gh variable set`):

| Змінна | За замовчуванням | Призначення |
|--------|------------------|-------------|
| `AGENT_PAUSED` | — | `true` — аварійний вимикач: агент не бере нових задач |
| `AGENT_DAILY_PR_CAP` | 10 | ліміт PR агента на добу (UTC) |
| `AGENT_BATCH_SIZE` | 3 | максимум задач в одному PR |
| `AGENT_MODEL` | `opus` | модель агентів |
| `AGENT_BUDGET_USD` / `AGENT_REVIEW_BUDGET_USD` | 10 / 3 | `--max-budget-usd`: для implement — на кожну задачу пакета, для рецензента — на запуск |

**Секрети** — лише в environment `agent`, до якого є доступ тільки з гілки main. Workflows з PR-гілок цих секретів не бачать.
- `CLAUDE_CODE_OAUTH_TOKEN` (через `claude setup-token`) або `ANTHROPIC_API_KEY`.
- `AGENT_GH_TOKEN` — fine-grained PAT **лише на цей репозиторій** з правами Contents, Pull requests і Issues (read/write). Прав
  на **Workflows немає навмисно**: агент фізично не може запушити зміну `.github/workflows/**`.

**Ізоляція агента:**
- Процес Claude не отримує жодного GitHub-токена. Він лише редагує файли й комітить локально.
- Пуш і створення PR виконує окремий крок після роботи агента. Коміти переносяться в чистий клон, тож git-config і хуки робочої копії не використовуються.
- Керувальні скрипти й промпти (`.github/agent/`) завжди беруться з main, а не з PR.
- `guard` працює через `pull_request_target`: workflow береться з main, код PR не виконується.
- Рецензент працює лише на читання: `--permission-mode dontAsk` і дозволені лише Read/Grep/Glob та `git diff/log/show`.
- Одночасно відкритий лише один PR агента. Для кожного PR — не більше 3 спроб фіксу, далі `needs-human`.

## 8. Що робить людина

1. **Один раз:** додає два секрети в environment `agent` (див. §7), пізніше — акаунт на хостингу (T50) і `BUG_REPORT_TOKEN` сервера на Render (fine-grained PAT лише на цей репозиторій, право Issues) для кнопки «Повідомити про баг».
2. **Правила:** схвалює або відхиляє `spec-change` PR.
3. **Гра:** грає й тисне «Повідомити про баг».
4. **`needs-human`:** розбирає рідкісні тікети; сповіщення приходять через GitHub.
